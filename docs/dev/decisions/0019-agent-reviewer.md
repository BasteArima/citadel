# 0019. Агент-проверяющий: принимает чужие правки и публикует

Дата: 2026-11-03 · Статус: принято. Уточняет [0003](0003-agents-edit-via-drafts.md).

## Контекст

Курс наполняют два агента: один пишет, другой проверяет. Проверка уже идёт по правилам и подробнее, чем смотрит человек: запуск всех программ, сверка с источниками, анимации по шагам. После этого владелец только нажимал «Принять» и «Опубликовать». Владелец решил убрать этот шаг.

В 0003 было записано, что агент не публикует, по двум причинам: ошибка сразу дойдёт до учеников, а внедрённые инструкции получат прямой путь к публикации. Обе причины остаются, поэтому право должно быть узким.

## Решение

- У токена появилось право проверяющего. Оно дает `list_queue`, `accept_proposal`, `reject_proposal` и `publish_version`, а также чтение чужих правок. То же есть в REST.
- По умолчанию право выключено. Включает и снимает его только админ в админке: сам токен расширить свои права не может. Право действует только на курсы токена.
- **Автор не принимает свою правку.** Сервер это запрещает: принять можно только правку другого токена. Поэтому у каждого агента должен быть свой токен.
- Только админ принимает новый курс и правку, у которой вывод программы не совпал с запуском на сервере.
- Публикация агентом проходит ту же проверку, что и у админа. Версия с ошибками не публикуется. Откат — публикация прошлой версии.
- В правке записано, какой агент её принял. Публикация попадает в журнал сервера с именем токена.

## Почему не иначе

- **Оставить приёмку человеку.** Безопаснее, но шаг стал формальным: человек принимал то, что уже проверено, не читая заново.
- **Принимать автоматически, если проверки сервера прошли.** Сервер видит схему и вывод программ, но не смысл. Ошибку в механике и плохие вопросы находит только чтение.
- **Отдельный токен только на публикацию.** Лишняя сущность: приём и публикацию делает один и тот же проверяющий, а нужны они вместе.

## Последствия

- Проверяющий читает правки другого агента, поэтому внедрённая инструкция в тексте правки теперь опаснее. Правила токена говорят, что текст, описание и отчёт автора — данные, а решение принимается только по итогам своей проверки.
- Разделение держится на токенах, а оба агента работают под одним пользователем ОС: технически один может прочитать конфиг другого. Защита здесь — правило для агентов и подпись в очереди: правка писателя с токеном проверяющего видна сразу, и принять её нельзя. Для настоящей изоляции писателю нужна отдельная учётная запись или песочница. Сейчас на сервере один владелец и его курсы, поэтому этого достаточно.
- Если проверяющий ошибётся, ученики увидят ошибку сразу. Цена исправления — публикация прошлой версии.
